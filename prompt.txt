# 1. REQUEST INSPECTION / INSTALLATION HANDOFF

There is currently no dedicated inspection data model.

Create the **minimum new Request-specific structure** necessary to store an inspection report associated with a Request.

The purpose is:

> The inspecting/consulting technician should be able to document the site thoroughly enough that the installing technician can understand the job almost as if they personally performed the inspection.

The inspection report should support the following approved information categories:

### Site Conditions / Observations

Information discovered by the inspecting technician about the installation site.

### Required Materials

Materials/components required for the planned work.

### Required Tools

Tools required by the installing technician.

### Installation Notes / Process

Practical instructions and observations describing how the installation should be approached.

### Inspector Recommendations

Recommendations made by the inspecting technician based on the site inspection.

Do not invent additional business requirements.

Do not introduce lifecycle states.

Do not change the Request workflow.

# TIMELINE BEHAVIOR

The final Request timeline should present meaningful Request activity in chronological order.

For example:

```text
Request submitted
↓
Staff reviewed request
↓
Inspection completed
↓
Inspection report added
↓
Inspection photos uploaded
↓
Quote created
↓
Payment received
↓
Technician assigned
↓
Technician accepted assignment
↓
Verification submitted
```

These are examples only.

Do not invent events that are not actually present in the existing system.

Use the events/actions that actually exist.

# TIMELINE DATA

Each timeline entry should expose, where available:

* Action
* Actor
* Timestamp
* Relevant details
* State transition information when applicable

Clearly distinguish lifecycle transitions from other actions where useful.
